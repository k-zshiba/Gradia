# リリース規約

## サイクルと番号

- `main`を常に検証可能な状態に保ち、通常は週1回程度を目安に機能をまとめてリリースします。日程による自動タグ作成は行いません。
- 不具合・セキュリティ修正は必要に応じて随時リリースします。
- SemVerの`MAJOR.MINOR.PATCH`を採用します。機能追加はMINOR、不具合修正はPATCH、1.0以降の互換性を壊す変更はMAJORです。0.xでの破壊的変更はMINORを上げ、変更履歴に明記します。
- 安定版タグは`v0.2.0`の形式です。確認用は`v0.3.0-rc.1`とし、通常アプリには自動配信しません。
- タグ・公開済みバイナリは変更・削除・上書きしません。問題があれば新しいPATCH版で修正します。ビルドに失敗した未公開Draft Releaseは、同じタグのワークフロー再実行で再生成できます。

## リリース前の操作

1. 対象の機能・修正PRを`main`へ取り込み、Windows checksの成功を確認します。
2. 最新の`origin/main`から`release/v0.3.0`のようなリリース準備ブランチを作ります。
3. `npm run release:version -- 0.3.0`で全マニフェストとロックファイルを揃えます。
4. `CHANGELOG.md`の`Unreleased`から今回の変更を`0.3.0`へ移し、空の`Unreleased`を残します。重大な変更・移行手順も含めます。
5. `npm run release:check -- v0.3.0`と開発手順のテストを実行し、バージョン・変更履歴を更新するPRを作成します。
6. PRの検証と確認が済んだら`main`へ取り込み、取り込まれたコミットのWindows checksが成功したことを確認します。
7. そのコミットにタグを付けてpushします。作業ブランチ上のコミットにはタグを付けません。

```powershell
git fetch origin
git switch main
git pull --ff-only origin main
git tag -a v0.3.0 -m "Gradia 0.3.0"
git push origin v0.3.0
```

この例では、手順6で確認したコミットが現在の`origin/main`の先頭であることを確認してから実行します。後続のPRが取り込まれている場合は、リリースPRが取り込まれたコミットを明示してタグを付けます。

`package.json`、`package-lock.json`のトップレベルとルートパッケージ、`Cargo.toml`、`Cargo.lock`、`tauri.conf.json`のバージョンがタグと異なる場合は公開しません。タグは`main`の履歴上のコミットに限ります。

## リリース用ブランチ

現在は最新の安定版だけを保守し、常設の`develop`・`release`ブランチは作りません。リリース準備ブランチも通常の作業ブランチと同様、PRを取り込んだら削除します。配布元は検証済みの`main`上のタグです。通常の開発手順は[ブランチ運用](branching.md)に記載します。

RCもリリース準備PRを`main`へ取り込んでから`v0.3.0-rc.1`を付けます。準備ブランチ名には公開予定の安定版番号を使い、例えば`release/v0.3.0`とします。取り込み後は削除し、次のRCや安定版の準備時は最新の`origin/main`から作り直します。RC中の修正は`fix/<目的>`から`main`へPRします。RCの確認中は、対象外の新機能を`main`へ取り込まず、`feature/<目的>`で保持します。

複数の安定版の同時保守は現在の運用には含めません。必要になった場合は、保守元のブランチ・公開元の検査・CI・更新配信先を別途設計します。現行の公開処理は`main`上のタグだけを許可します。

## 自動処理

`.github/workflows/release.yml`がタグpushで動作します。

1. タグ・バージョン・変更履歴を検査。
2. 依存監査、単体テスト、ブラウザーテスト、Rust整形・テストを実行。
3. Windows x64用NSISインストーラーを作成し、更新用署名を生成。
4. Draft Releaseに全ファイルをアップロード。
5. 安定版は現在のLatestより新しいことを確認してから公開し、Latestに指定。RCはPrereleaseとして公開し、Latestを変更しない。

`requireSignedVersion`を有効にし、署名コメントのバージョンがタグと一致しない成果物は公開しません。配布済み0.2.0・0.2.1の署名にもバージョンが記録されています。外部Actionの固定SHAを更新するときは、公式リポジトリのコミットであることと変更内容を確認してください。

公開するファイルは次のとおりです。

| ファイル                     | 用途                                            |
| ---------------------------- | ----------------------------------------------- |
| `Gradia_X.Y.Z_x64-setup.exe` | 手動導入とアプリ内更新に使うインストーラー      |
| 同名`.exe.sig`               | Tauriの更新署名                                 |
| `latest.json`                | バージョン・変更内容・Windows x64の取得先・署名 |
| `SHA256SUMS`                 | インストーラー・署名・JSONのチェックサム        |

モデル、llama-server、Codex、ユーザー資料・資格情報は配布物に含めません。Tauriの更新署名はWindowsのAuthenticodeコード署名とは別のものです。

## 署名鍵

- 公開鍵は`src-tauri/tauri.conf.json`へ埋め込みます。秘密鍵はGitHub Actionsの`TAURI_SIGNING_PRIVATE_KEY` Secretだけに渡し、ログやGitに保存しません。
- このリポジトリのSecretは初回設定済みです。ローカルバックアップは`.tools/release-keys/gradia.key.dpapi`にあり、生成したWindowsユーザーのDPAPIで暗号化されています。
- 別PCへの移行に備え、秘密鍵の復元・安全なバックアップ方法を所有者が管理してください。GitHub Secretsは登録後に値を読み出せません。鍵紛失時に単に公開鍵を置き換えても、配布済みアプリは新しい鍵を信頼できません。
- ローカルで署名付きビルドを行う場合は、安全に復元した鍵のパスまたは内容を`TAURI_SIGNING_PRIVATE_KEY`へ渡し、`npm run package`を実行します。署名不要の確認用は`npm run package:unsigned`です。

## アプリの更新動作

起動時にGitHub Release APIで最新安定版を確認し、Asset APIから`latest.json`を取得します。インストーラーも同じReleaseのAsset APIから取得し、Tauri標準の公開鍵検証を行います。公開ReleaseのためGitHubへのログインは不要です。APIの利用制限や通信断は更新確認失敗として扱い、閲覧を継続します。

新しいバージョンがあると確認画面を表示し、「はい、更新する」でのみインストーラーの取得・署名検証を進めます。「今は更新しない」を選ぶと、現在のバージョンを維持します。次回起動またはヘッダーのバージョンボタンから再確認できます。

取得と検証が成功してから読書位置を保存し、実行中ジョブの中断・履歴保存とモデル子プロセスの終了を待ちます。NSISで更新後に自動再起動します。取得・署名検証に失敗した場合はインストールせず、閲覧を継続できます。

資料・モデル・設定・DPAPI資格情報の保存先識別子`local.study-tool.desktop`は変更しません。今後DBを変更するときも、既存データを保持したまま移行することを前提とします。

旧Study Tool / 自動更新導入前の0.1.0には更新確認機能がありません。最初の署名付きGradiaを手動インストールした後から、アプリ内更新を利用できます。

## 公開後の確認と復旧

- GitHub Releaseに4種類のファイルが揃い、`latest.json`の版・URL・署名が公開物と一致することを確認します。
- 初回導入、更新の拒否、同意後の更新、データ・認証の保持、オフライン時の継続利用を確認します。
- 不具合があれば、正常な動作に戻す新しいPATCH版を公開します。自動ダウングレードはしません。
- 配布済みReleaseの差し替えによる修正は行いません。緊急に配信を止める必要がある場合はRelease運用を所有者が判断し、利用者へ手順を案内します。
